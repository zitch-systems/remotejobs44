# Backend + Frontend Audit — 2026-07-06

Critical audit of the whole product surface: marketing web, member web app, admin
panel, agent portal, cron/ingestion, Paystack payments, Supabase (schema/RLS/storage/
edge functions), and the Expo mobile app. Findings were cross-checked against the
**live Supabase project** (`gnyilmahiyddplsrrhoq`, read-only) — bucket flags, RLS
posture, and the security advisors.

## Headline

The codebase is in **very good shape**. Auth/session, admin authorization, the
Paystack money path (web webhook + mobile edge functions), SSRF, RLS, XSS, and rate
limiting were all verified secure. The real defects clustered in two places the prior
web-focused audits hadn't reached: **CV storage** and the **mobile AI edge functions**.

Baseline: `tsc --noEmit` clean, `eslint` 0 errors, 417/417 unit tests pass.

## Fixed

### 1. CV storage — private bucket vs. public-URL mismatch (shipped in #148)
- **Mobile CV upload was broken.** `mobile/src/lib/profile.ts` stored `getPublicUrl()`
  for a bucket that is private (`public=false`, confirmed live), so the link 401s
  ("Bucket not public") and "View CV" never worked. Now stores the storage **path**
  (like the web `/api/cv` route) and mints a signed URL on demand; legacy full-URL
  rows are transparently recovered.
- **`migration_v39` would expose CVs on a fresh deploy.** It declared the bucket
  `public=true` with no SELECT policy — a migration-based provision would have made
  every PII-laden CV world-readable by URL. Corrected to a private bucket with the
  full own-folder policy set.
- **Missing UPDATE policy broke CV replacement.** The live `cvs` bucket had
  insert/select/delete but no UPDATE policy, so Storage upsert re-uploads ("Replace
  CV") were RLS-denied. Added the own-folder UPDATE policy to `setup.sql` and a
  standalone `migration_v61_cv_update_policy.sql` for existing installs.

### 2. Mobile AI edge functions had no entitlement gate — HIGH (this PR)
`supabase/functions/ai-cv-review`, `ai-interview-prep`, and `ai-cover-letter`
authenticated the JWT but **never checked the plan or rate-limited**, while the web
`/api/ai/*` routes do both. The mobile client's `canUseAI` (a render-only paywall) was
the *only* gate, so any signed-in free user could invoke the functions directly and
receive unlimited Pro-only AI output — an entitlement bypass **and** unbounded LLM
spend. The mobile audit's adversarial verifiers confirmed this 3/3.
- **Fix:** each function now resolves the caller's effective plan (via their own
  JWT + profiles RLS, honoring `plan_expires_at`) and rejects non-paid callers with
  403, mirroring `entitlements.canUseAI`/`isPaid`. The client paywall remains UX-only.

### 3. Payment reconcile could re-credit an already-redeemed charge — HIGH (this PR)
`lib/paystack/reconcile.ts` keyed idempotency on `subscriptions.paystack_reference`,
but that table is keyed on `user_id` and its reference is **overwritten on every
renewal**. A user with ≥2 successful charges in the 7-day reconcile window whose
access had lapsed would have the *older* (overwritten) charge re-credited — repeated
free access. Verify + webhook already use the durable `paystack_transactions`
(reference = PK) ledger; reconcile did not.
- **Fix:** reconcile now checks and **claims** the reference in `paystack_transactions`
  before crediting (with claim-release on profile-update failure), so a charge is
  recorded once and never re-credited.

### 4. Public jobs API — 500 via prototype key — LOW (this PR)
`app/api/jobs/route.ts` did `REGION_TERMS[userInput]` with bare truthiness, so
`?country=constructor` (or `toString`, …) resolved to an inherited `Object.prototype`
function and `.map`/`[0]` threw a 500 (error-log noise / cheap DoS). Guarded both
lookups with `Array.isArray`.

## Documented — needs a decision or a follow-up (not changed here)

### A. Automated `ats-refresh` cron undoes admin company removals — MEDIUM
`/api/admin/companies/remove` **soft-deletes** (`is_active=false`). The daily
`lib/ats-refresh.ts` sweep unconditionally flips still-listed ATS jobs back to
`is_active=true`, so removing an ATS-sourced company reverts automatically within ~24h.
The in-code assumption ("no company has ever been manually removed") breaks the moment
the remove feature is used.
- **Recommended fix:** add a `jobs.admin_removed boolean default false`; set it in the
  remove route; have `markSeen` reactivate only rows where `admin_removed = false`.
  Decide whether the *manual* "Refresh" flow should clear the flag (it likely should,
  since that's an explicit admin action). Needs a migration + product decision, so it
  is flagged rather than shipped blind.

### B. Mobile AI functions still lack a per-user rate limit — MEDIUM
The entitlement gate (fix #2) stops free-user abuse, but a *paid* user can still call
the AI functions without a daily cap (the web routes cap at 20/day + an IP cap). Edge
functions have no shared memory, so a robust cap needs a DB-backed daily counter
(e.g. an `ai_usage_daily(user_id, day, count)` table). Recommended as hardening.

### C. Refunds/chargebacks don't reverse agent commission — LOW
The webhook has no `refund`/`charge.refund` handler, so a recorded
`agent_commissions` row stays `pending` after a refund. Commissions are manually
reviewed before payout, so impact is low, but a refund handler that flips the row to
`reversed` would close it.

### D. Mobile uploads bypass server-side file validation — LOW
Mobile writes to Storage directly (RLS-scoped to the user's folder), so it skips the
web `/api/cv` magic-byte/type/size checks and rate limit, and CV filenames are
timestamped (`cv-<ts>.<ext>`) so replacing a CV accumulates orphaned objects. Low risk
(RLS still confines access); consider routing mobile uploads through a validating
function or a fixed key + periodic cleanup.

### E. Minor
- `render-js` puppeteer sub-resource fetches aren't DNS-pinned (a documented residual
  of the SSRF guard; realistic static-record rebinding is already blocked).
- `/login` "Remember me" checkbox is non-functional (session always persists).
- In-app "Change password" recovery email omits `redirectTo`, so its link doesn't
  return to the app.
- Supabase advisors: `is_admin(uuid)` SECURITY DEFINER is `EXECUTE`-able by `anon`
  (info disclosure — needs a known UUID); `pg_trgm`/`pg_net` live in the `public`
  schema. Both are low-priority hardening.

## Verified secure (no change needed)

- **Paystack webhook:** HMAC-SHA512 + constant-time compare, amount-vs-plan validation,
  dual-layer idempotency (`paystack_transactions` PK + webhook-event dedup).
- **Mobile payments:** price set server-side in the edge function; verify re-checks
  `metadata.user_id` against the caller + amount + idempotency.
- **Admin authz:** `requireAdmin` (role + hardcoded list + `suspended` kill-switch +
  email 2FA); every `/api/admin/*` mutation gated, allow-listed, and audit-logged; the
  `promote` endpoint is disabled (410).
- **RLS:** all 20 public tables have RLS enabled; the two policy-less tables
  (`admin_2fa_codes`, `paystack_transactions`) are correctly default-deny (service-role
  only). CV bucket private; user-scoped queries filter on `auth.uid()` (no IDOR).
- **SSRF:** DNS-aware guard blocks private/loopback/link-local/metadata + `*.localhost`.
- **Injection/XSS:** supabase-js parameterization + LIKE-wildcard escaping; feed parser
  is regex-based (no XXE); every `dangerouslySetInnerHTML` is escaped JSON-LD only.
- **Auth UX:** open-redirect guard on `?next=`; extensive random-logout protection in
  middleware + `AuthSyncProvider`; contact form strips header-injection + HTML-escapes.

## Method
12 backend/frontend subsystem finders + 3 mobile finders, each candidate finding put
through independent adversarial verifiers, plus manual review of every high-risk file
and read-only checks against the live Supabase project. (Some verifier passes hit a
session rate limit; those findings were confirmed by direct code reading instead.)
